# React Native weather app — fixes verified, remaining gaps (v2)

All eight issues from the first review have been addressed. The duplicate search path is gone, unit persistence works via AsyncStorage, the FlatList/ScrollView nesting was replaced with a mapped ScrollView, coordinate validation gates every API call, the clear-all operation is atomic, and the unit change correctly invalidates cached data by resetting `lastUpdated` to null. The codebase is cleaner and more consistent as a result.

**Watch for:** `removeLocation` still reads from a stale closure when called individually, so rapid successive deletions may persist an incorrect list (confirmed); the `SearchBar` debounce timer is not cleaned up on unmount, which can fire `setState` on an unmounted component (confirmed); wind speed in `WeatherDetails` is hardcoded to "m/s" regardless of the user's unit setting (confirmed).

## High-level view

The stale-closure pattern that was fixed for clear-all still exists in the individual `removeLocation` path: each call filters `state.savedLocations` from the closure at memoization time, so two rapid deletes in the same render frame will both compute their persistence array from the same stale snapshot, and the second delete's persist call overwrites the first. Under normal usage (one delete at a time via Alert confirmation) this is unlikely to trigger, but the pattern is structurally unsound.

The `SearchBar` component stores a `setTimeout` ID in a ref but never clears it when the component unmounts. If the user navigates away from the Locations tab during the debounce window, the callback fires on a stale `setSearchResults` / `setIsSearching` — a classic React Native memory-leak warning pattern.

The `WeatherDetails` component hardcodes wind speed as `m/s` regardless of whether the user has selected imperial units (which would return mph from the API). The rest of the UI correctly passes `temperatureUnit` through, but this one detail grid cell ignores it.

## Stale closure in removeLocation persistence

The clear-all path was correctly fixed with an atomic reducer action, but individual removes still exhibit the original pattern:

```typescript
const removeLocation = useCallback(
  async (id: string) => {
    dispatch({ type: 'REMOVE_LOCATION', payload: id });
    const updated = state.savedLocations.filter((loc) => loc.id !== id);
    await persistLocations(updated);
  },
  [state.savedLocations, persistLocations]
);
```

The dispatch correctly updates the reducer synchronously, but `persistLocations(updated)` derives the array from `state.savedLocations` — the closure value at memoization time, not the post-dispatch value. If the user taps delete on one location, confirms via Alert, then immediately taps delete on another before the component re-renders with the new dependencies, the second call's `state.savedLocations` still contains the first item. The persisted JSON will include the first item that was supposedly deleted.

The practical impact is low because the Alert confirmation dialog blocks rapid successive deletes. But the architectural inconsistency with the atomic clear-all approach makes this a latent bug that would surface if the confirmation dialog were ever removed (e.g., for swipe-to-delete).

A cleaner pattern: persist inside a `useEffect` that watches `state.savedLocations`, so any reducer state change automatically triggers persistence without needing to manually compute the post-dispatch array.

## SearchBar unmount leak

```typescript
const timerRef = useRef<ReturnType<typeof setTimeout> | null>(null);

const handleChangeText = useCallback(
  (text: string) => {
    setQuery(text);
    if (timerRef.current) clearTimeout(timerRef.current);
    timerRef.current = setTimeout(() => {
      onSearch(text.trim());
    }, debounceMs);
  },
  [onSearch, debounceMs]
);
```

If the user types a character and navigates to a different tab within 500ms, the timeout fires after the component has unmounted. In React Native with Hermes, this produces a "Can't perform a React state update on an unmounted component" yellow-box warning. The fix is a one-line `useEffect` cleanup:

```typescript
useEffect(() => {
  return () => {
    if (timerRef.current) clearTimeout(timerRef.current);
  };
}, []);
```

## Wind speed unit mismatch in WeatherDetails

`WeatherDetails` renders:

```typescript
{
  icon: 'speedometer-outline',
  label: 'Wind',
  value: `${weather.windSpeed} m/s`,
}
```

The OpenWeatherMap API returns wind speed in m/s for `units=metric` and mph for `units=imperial`. Since the component doesn't receive the current unit, it always displays "m/s" — which is incorrect when the user has selected Fahrenheit. The `formatWindSpeed` utility in `helpers.ts` already handles this correctly; `WeatherDetails` just needs to accept a `unit` prop and use it.
