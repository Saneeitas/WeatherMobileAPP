# React Native Expo weather app — full greenfield implementation

A complete weather mobile app built from scratch with React Native/Expo, featuring current weather, 5-day forecast, city search with saved locations, and a settings screen for unit toggling. The architecture uses React Context + useReducer for state, a service layer wrapping the OpenWeatherMap API, and tab-based navigation across four screens. The implementation includes input sanitization, request timeouts, structured error mapping, and debounced search — a solid foundation that covers the essential security and UX patterns for a read-only weather viewer.

**Watch for:** API key exposed in plain URL query strings without transport pinning (confirmed); stale closure in `fetchWeather` causes unit changes to require a manual refresh (confirmed); `LocationService.searchCity` bypasses the sanitization that `WeatherService.searchCity` applies (confirmed); no persistence of temperature-unit preference across app restarts (confirmed); the "clear all locations" implementation fires N individual async deletes with a race condition against stale state (confirmed).

## High-level view

The service layer (`weatherApi.ts`) is the strongest part of the codebase: it validates the API key before making requests, maps HTTP status codes to domain-specific error types, enforces request timeouts, and sanitizes search input. The duplicate `searchCity` in `locationService.ts` does none of this, creating an inconsistency in the security posture of the search path depending on which screen initiates it.

State management splits weather and location concerns into separate contexts, connected by the screens that consume both hooks. The `fetchWeather` callback captures `state.temperatureUnit` via its `useCallback` dependency, but because the weather and unit state live in the same reducer, changing the unit doesn't trigger a re-fetch — the user sees stale data in the old unit until they manually refresh or navigate away and back.

The UI is clean and well-structured: gradient backgrounds adapt to time of day and temperature, the daily forecast includes a proportional temperature bar, and the component tree is flat enough to avoid prop-drilling. The one structural concern is the `HomeScreen` embedding a `FlatList` inside a `ScrollView`, which breaks virtualization on Android and produces a console warning.

Data persistence covers saved locations via AsyncStorage but does not persist the temperature unit or last-fetched weather, so users restart the app in metric every time and wait for a fresh API call regardless of cache age.

1. **API key in URL query string** — The key travels in plaintext URL params. Use request headers or a proxy backend to avoid key leakage in logs and caches.
2. **Stale unit in fetchWeather closure** — Changing the temperature unit doesn't trigger a re-fetch. Add `temperatureUnit` to the effect dependency that calls `loadWeather`, or trigger a re-fetch when the unit changes.
3. **Unsanitized search in LocationService** — `LocationService.searchCity` passes user input through `encodeURIComponent` only, skipping the character-class sanitization applied in `WeatherService.searchCity`. Centralize search through one code path.
4. **Clear-all-locations race condition** — `handleClearLocations` iterates `savedLocations` calling `removeLocation` per item, but each call uses the array from the closure at call time, not the progressively-shrinking array. Add a `CLEAR_ALL` action that operates atomically.
5. **Temperature unit not persisted** — `temperatureUnit` resets to `'metric'` on every app start. Persist it to AsyncStorage alongside saved locations.
6. **FlatList inside ScrollView** — `HomeScreen` nests a horizontal `FlatList` inside a `ScrollView`, which disables virtualization and triggers a VirtualizedLists warning on Android.
7. **No coordinate validation** — The weather API functions accept arbitrary `lat`/`lon` without range checks. Invalid coordinates would produce a 400 from OpenWeatherMap with a generic error message.
8. **Duplicate searchCity implementations** — Two independent `searchCity` functions exist (`WeatherService` and `LocationService`) with different error handling and sanitization behavior. Only one should exist.

## Dual search paths and sanitization gap

`WeatherService.searchCity` in `weatherApi.ts` applies `sanitizeQuery` which strips non-alphanumeric characters (except spaces, commas, hyphens, periods, and apostrophes) and truncates to 100 characters. `LocationService.searchCity` in `locationService.ts` only calls `encodeURIComponent` on the raw query, meaning characters like `<`, `>`, `{`, `}`, and backticks pass through to the URL. The `LocationsScreen` calls `LocationService.searchCity`, so the production code path for user-facing city search lacks the sanitization guardrails.

The fix is simple: delete `LocationService.searchCity` and have `LocationsScreen` call `WeatherService.searchCity` instead, or extract the sanitization into a shared utility.

## API key transport

The API key is appended as an `appid=` query parameter in every request URL:

```typescript
const url = `${Config.api.baseUrl}/weather?lat=${lat}&lon=${lon}&units=${unit}&lang=${Config.defaults.language}&appid=${Config.api.key}`;
```

Query parameters appear in browser history, proxy access logs, CDN caches, and crash reports. For a mobile app where fetch requests go directly to the API, the practical exposure is limited to device-local network inspection, but the key is still visible to any intermediate proxy or debugging tool. A backend proxy that holds the key server-side would eliminate this exposure entirely — though for a free-tier OpenWeatherMap key the risk is proportional.

## Unit change doesn't trigger refresh

In `WeatherContext`, `fetchWeather` is memoized with `[state.temperatureUnit]` as a dependency:

```typescript
const fetchWeather = useCallback(async (lat, lon) => {
  // ...uses state.temperatureUnit to build the URL
}, [state.temperatureUnit]);
```

However, the `HomeScreen` effect depends on `loadWeather` (which depends on `fetchWeather`), so changing the unit does regenerate the callback — but the effect also checks `if (!currentWeather || !lastUpdated || Date.now() - lastUpdated > Config.cache.weatherTTL)`, so if data was fetched within the last 10 minutes, the effect exits early and the user sees temperatures in the old unit. The UI components just render `weather.temperature` raw, relying on the API to return the correct unit rather than doing client-side conversion. This means the only way to see the correct unit is to wait for cache expiry or pull-to-refresh.

## Clear-all-locations race

```typescript
onPress: () => {
  locationState.savedLocations.forEach((loc) => {
    removeLocation(loc.id);
  });
}
```

Each `removeLocation` dispatches `REMOVE_LOCATION` and then calls `persistLocations` with the filtered array. But because `removeLocation` is memoized with `[state.savedLocations, persistLocations]`, the second and subsequent calls within the same render frame still see the original array. The persisted result depends on execution order and may leave locations behind. A single `CLEAR_ALL` reducer action that empties the array and persists once would be correct.

## FlatList nested in ScrollView

`HomeScreen` renders:

```tsx
<ScrollView>
  <WeatherCard />
  <FlatList data={todayHourly} horizontal />
  <WeatherDetails />
</ScrollView>
```

React Native warns that VirtualizedLists should never be nested inside plain ScrollViews because the outer scroll container prevents the inner list from calculating which items are visible. For a horizontal hourly list that rarely exceeds 24 items this is cosmetically harmless, but it triggers a yellow-box warning and technically disables recycling. Replacing the FlatList with a `ScrollView` (horizontal) containing mapped items would silence the warning without behavioral change.

## Missing persistence for user preference

The temperature unit lives only in `WeatherState` initialized to `Config.defaults.unit` (`'metric'`). There is no `AsyncStorage.getItem` on mount to restore a previously-chosen unit, and no `AsyncStorage.setItem` when the user toggles. The `Config.storage.settingsKey` constant exists but is never used.

## No test coverage

No test files are present. The task metadata acknowledges tests were skipped due to network constraints, but the test infrastructure (jest config in package.json, `@testing-library/react-native` in devDependencies) is in place for future additions. Key areas that would benefit from unit tests: the `mapCurrentWeather` and `mapForecastData` response mappers, the `sanitizeQuery` function, the `weatherReducer`, and the `locationReducer`.
